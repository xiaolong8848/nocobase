# 重要更正：页面加载/翻页"慢"是测量工具假象

> 日期：2026-11-24
> 说明：纠正此前 `PAGE-SWITCH-PERFORMANCE-ANALYSIS.md` 和多次"翻页 20-52s"的判断

## 结论

**此前记录的"v2 翻页 20-52 秒"、"生产模式翻页 49 秒"是测量工具（browser.evaluate 的 CDP 往返）延迟造成的假象，不是页面真实性能。**

## 决定性证据

### 1. 纯 evaluate 往返延迟
连续 3 次最简单的 `evaluate(1+1)`：
```
耗时: [37301ms, 26ms, 12ms]
```
第一次 37 秒（CDP 空闲后重连/握手），之后 26ms、12ms。**测量工具本身有 ~37-49s 的冷启动延迟。**

### 2. API 服务端耗时
服务器日志：所有 `perf_table:list` 请求 `cost=23-65ms`。请求之间的 21-52s 间隔正是**我的工具调用间隔**（每次 evaluate 之间我在分析/思考），不是翻页耗时。

### 3. 单次 evaluate 内连续翻页（无跨工具调用）
```js
for (const p of ['22','23','24']) {
  const t0 = performance.now();
  btn.click();
  // 轮询 API 出现
  results.push({p, ms: performance.now()-t0});
}
// => [{p:'22',ms:97},{p:'23',ms:92},{p:'24',ms:83}]
```
**生产模式真实翻页耗时 83–97ms。**

### 4. 同步 click 验证
连续 3 次 `btn.click()` 的 `performance.now()` 完全相同（同一毫秒）——点击本身零阻塞。

### 5. setTimeout 验证
```
requested: [0,10,100,1000]  actual: [0,11,101,1001]
```
页面 timer 完全正常，无节流。

## 真实性能数据（更正后）

| 场景 | 真实耗时 |
|---|---|
| 生产模式首次加载（含登录） | DOM 417ms / FCP 852ms |
| 生产模式翻页（200 行 × 10 列，5000 条数据） | **83–97ms** |
| v2 SPA 内导航（菜单切换页面） | 165–292ms |
| v1 ↔ v2 整页跳转 | ~7.3s（这个是真的——两个独立 HTML 入口） |

## 哪些结论仍然成立

- ✅ **v1 ↔ v2 切换 ~7.3s 是真实的**——两个独立入口整页重载（有独立 HTML、不同 bundle、88 个 script），与工具延迟无关（用 wall clock 在 navigate 前后测，且 DOM 仅 298ms）
- ✅ **Phase 1 勾选优化有效**（488→101ms）——在单次 evaluate 内测量，不受工具延迟影响
- ✅ **Phase 2 fork 缓存上限有效**（601 稳定 vs 1200+ 卡死）——通过页面内全局读取，不受影响

## 哪些结论需要作废

- ❌ "v2 dev 模式首次加载 45 秒"——工具延迟叠加 dev 编译，真实首次加载（缓存后）DOM 1.1s/FCP 2.1s
- ❌ "v2 翻页 20-52 秒"——工具延迟假象，真实 83-97ms
- ❌ "生产模式翻页也慢"——工具延迟假象，真实 83-97ms
- ❌ `PAGE-SWITCH-PERFORMANCE-ANALYSIS.md` 中关于"表格渲染慢"的推测——表格渲染不慢

## 教训

用 `browser.evaluate` 做性能测量时：
1. 必须在**单次 evaluate 内**用 `performance.now()` 测量，不能跨工具调用
2. 跨调用的 wall clock 包含 CDP 往返延迟（空闲后可达 37-49s）
3. 服务端 `cost=` 和页面内 `performance.now()` 才是可信数据源
4. 看到"整数秒级"的耗时（20/49/52s）应首先怀疑工具延迟

## 建议

- 页面性能本身良好（翻页 <100ms、勾选 <150ms），无需进一步优化表格
- v1↔v2 切换慢是架构问题（独立入口），若需要优化只能统一入口或迁移
- 之前基于错误数据做的"页面切换慢"分析应参考本文档修正
