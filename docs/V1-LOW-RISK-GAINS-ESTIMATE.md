# v1 低风险优化的成效预估

> 分支：`perf/table-block-refactor`　|　日期：2026-11-24
> 说明：以下为**基于代码机制的估算区间**，非实测值；实际收益必须用 Phase 0 基线验证

---

## 0. 总体判断

**低风险优化能改善"交互卡顿"，但对"超宽表首屏"帮助有限——因为不解决根本瓶颈（无虚拟化、全量 DOM）。**

| 场景 | 预估收益 | 说明 |
|---|---|---|
| 常规表（50–100 行 × 10–15 列）的**交互**（勾选/翻页/刷新） | **15–40%** | 主要来自 JSON.stringify 依赖修复 + SubTable 门控 |
| 常规表的**首屏** | **5–20%** | 来自死代码快路径，但只对纯文本列有效 |
| 纯文本为主的表首屏 | **15–30%** | 快路径绕过每格 `new Schema` 的收益最大化 |
| 含 SubTable / 嵌套显示字段的表 | **20–50%**（该部分交互） | linkage hook 门控省掉每格的变量解析 |
| 226 行 × 32 字段超宽表（历史卡顿场景） | **10–25%**，首屏仍可能 3–5 秒 | 6400+ DOM 节点是根本瓶颈，低风险优化不触及 |
| 窗口 resize 卡顿 | 基本消除（>90%） | 但这是低频操作，体感提升有限 |

---

## 1. 逐项收益拆分

### V1-1 `optimizeTextCellRender` 快路径 — 收益最大但有限制
**机制**：当前每格 `TableCellRender` → `NocoBaseRecursionField` → `new Schema(schema)` + `createMergedSchemaInstance`（`NocoBaseRecursionField.tsx:274-277,309-320`），且每格新建 `basePath` 数组（`Table.tsx:130`）。快路径让纯文本格直接渲染，跳过这套 Formily 管线。

**预估**：
- 纯文本列占比高的表：首屏 **15–30%**
- 混合列（含关联/编辑/状态）：**5–15%**（因为大部分格仍走原路径）

**限制**：必须保留 ACL 白名单（`Table.tsx:188`）、联动样式（`:687-709`）、省略/tooltip（`:245-255`）——这些检查本身有成本，所以快路径不是"零成本绕过"。且这是**死代码复活**，需要新写逻辑，不是开一个现成开关。

### V1-3 `JSON.stringify` 依赖修复 — 交互收益
**机制**：`rowSelection` 用 `JSON.stringify(rowSelection)` 当依赖（`:1086`）会丢弃函数，导致 handler 陈旧；pagination、getRowKey、rowClassName 同理。换成结构化 comparator 后，useMemo 命中更准确。

**预估**：交互重渲染 **10–25%**（不是首屏）。注意 v1 已有 `BodyRowComponent` 的 memo hack（`:660-683`），部分收益被抵消。

### V1-5 SubTable linkage 门控 — 特定场景高收益
**机制**：`association-field/Table.tsx:487-509` 每格无条件调用 `useSatisfiedActionValues`（内部 `useVariables`/`useLocalVariables`/`useEffect`），主表用 `!_.isEmpty(styleRules)` 门控（`:700-703`），副本没有。

**预估**：含 SubTable 的场景 **20–50%**（该部分）；无 SubTable 的表 **0**。

### V1-7 resize 无用重渲染 — 体感优化
**机制**：`useBlockSize.ts:179-204` 每次 debounced resize 设 `tableWidth`，但 `Table.tsx:1192` 只取 `height`，宽度状态更新白白触发整表重渲染 → 通过 V1-2 的 columns 重建放大。

**预估**：resize 操作 >90% 改善，但低频，整体体感提升小。

## 2. 为什么不会有质变（根本瓶颈）

低风险优化**不触及**以下根本问题：

| 根本瓶颈 | 影响 | 为何低风险不碰 |
|---|---|---|
| **无虚拟化**，全量挂载当前页所有行列 | 226×32 = 6400+ DOM 节点，首屏 5 秒的主因 | v1 无 virtual prop，实现需重写 Formily 每格组件 + 三个 body 组件（高风险） |
| **每格 Formily `new Schema`**（绝大多数列） | 每格成本，快路径只覆盖纯文本 | 去 Formily 破坏子表/编辑/联动/设计器（高风险） |
| **官方已吃掉大头** | PR #5438 首屏 -50%、PR #6888 越用越慢 | 剩下的都是边际收益 |

**因此**：历史反馈的 226 行 × 32 字段"首屏 5 秒、内存 2G"场景，低风险优化后可能降到 3.5–4 秒——有改善，但仍达不到"可用"。要质变必须虚拟化（高风险）。

## 3. 与 v2 同投入对比

| | v1 低风险（1–2 周） | v2 Phase 1–2（约 2 周） |
|---|---|---|
| 首屏 | 5–30%（视列类型） | 持平至 40%（Phase 3 才显著） |
| 交互 | 15–40% | **50–80%**（props 稳定是精准打击） |
| 插件风险 | 31 插件耦合（但低风险项不改契约） | 少 |
| 长期价值 | 低（legacy） | 高 |
| 质变潜力 | 无（需虚拟化） | 有（定点虚拟） |

**同样 2 周，v2 的交互收益（50–80%）高于 v1（15–40%），且 v2 有后续质变路径。**

---

## 4. 决策建议

1. **若只是想快速缓解 v1 页面卡顿**：做 V1-1 + V1-3 + V1-5 + V1-7（1–2 周），预期交互 15–40%、首屏 5–30%，是性价比合理的投入
2. **若追求质变**：v1 必须上虚拟化（高风险 6 周+），不如把预算转 v2
3. **若已在迁移 v2**：不建议在 v1 上花时间——低风险收益有限，且会分散 v2 资源

---

## 5. 一句话回答

**Q：v1 低风险改善预估有多大成效？**

**A：交互 15–40%、首屏 5–30%（纯文本多的表可达 30%），含 SubTable 的场景该部分可达 20–50%。但这是边际收益——不解决无虚拟化、全量 DOM 的根本瓶颈，226×32 超宽表仍可能 3–5 秒。同样 2 周投入，v2 的交互收益（50–80%）和长期价值都明显更高。除非你还有大量 v1 页面要长期维护，否则建议把预算留在 v2。**
